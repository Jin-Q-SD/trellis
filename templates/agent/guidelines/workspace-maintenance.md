# 工作区维护规则

`agent/` 之外的目录是**人的空间**，首先要让人读得懂、找得到。agent 在这里的原则是：多做加法，少做改动；重组先问，删除只建议。

## 四档权限

| 操作 | agent 能否直接做 | 例子 |
|---|---|---|
| 新增 | 可以 | 新建文件、出新版本、按约定建子目录、更新 README |
| 修正 | 可以，但要在当次 memory 里记一笔 | 移动或改名之后修复引用链接，同步 README |
| 重组 | 先提方案，等用户确认 | 合并或拆分子目录、批量迁移已有文件 |
| 删除 | 只提建议；用户同意后移进 `_delete/` | 重复文件、废弃文件 |

## 更新时机

- **写入时**：在某个目录新增或修改了文件后，如果这个目录的"重点内容"变了，顺手更新它的 `README.md`。小改动不动 README，避免无意义的改动。
- **会话结束时**：更新根目录 `README.md` 的"当前进展"（只保留最近两三条），以及 `agent/PROJECT.md` 的当前状态。
- **里程碑时**（交付、阶段完成）：归档旧版本，打包交付物，检查各目录 README 是否准确。
- **用户要求时**：`/trellis tidy` 做一次全面体检。

## 项目信息补充

init 时没确定的信息，会在 `agent/PROJECT.md` 里标成"待补充"。之后在对话中得知新信息时，按下表顺手更新，不需要专门问用户：

| 得知了什么 | 更新什么 |
|---|---|
| 目标、受众、交付物、约束、截止时间 | `agent/PROJECT.md` 对应的段落；一句话描述有变化时，同时改 `README.md` 和 `AGENTS.md` 的开头 |
| 项目要开始做一种新的工作（比如开始做调研、开始写代码） | 运行 `python3 agent/tools/scripts/add_dir.py <research\|docs\|design\|deliverables\|app> [--app-slug x]`，它会建目录、生成 README，并同步 trellis.json、目录地图和 README.md |
| 要和别人协作、要放 GitHub、要开源 | 按 [version-control](version-control.md) 开启或切换模式。**这一项要先问用户** |
| 文件名语言要换 | 改 `trellis.json` 的 `filename_lang` 和 `naming.md`。已有文件不批量改名，除非用户要求 |

## 版本和归档

- 新版本存为 `-v02`、`-v03`……旧版本移进**同一目录下**的 `_archive/`。这样目录里平时只看到最新版，旧版也不会丢。
- **用户的修改优先**：如果一个文件在 agent 上次记录之后被用户改过（比较修改时间，或者对照 memory 里的记录），不覆盖它，另存为新版本。
- **用户的整理优先**：用户手动移动或改名了文件，agent 就跟着更新 README 和引用，不改回去。如果用户反复用同一种方式调整，就提议把它写成规则。

## `_delete/`：等待删除区

- 用户同意删除后，把文件移进项目根目录的 `_delete/`，**保留原来的目录层级**，例如 `_delete/design/references/xxx.png`。
- 在 `_delete/README.md` 的清单里登记：移入日期、原路径、原因。恢复时照着清单放回去。
- 只有用户明确说"清空 delete"之类的话，才真正删除。删之前先给一份摘要（文件数、总大小、最早的移入日期），用户最后确认一次再删。
- `_delete/` 超过 1GB 时，在会话里提醒一句，不要自己清理。
- `_archive/` 放有保留价值的旧版本，`_delete/` 放等待删除的东西。不要把 `_archive/` 里的东西自动挪进 `_delete/`。
- **例外**：已经纳入 git 管理的应用代码，用户同意后用 `git rm` 删除，不移进 `_delete/`，因为 git 历史就能找回。
- **hook 守卫**：在 Claude Code 里，`.claude/settings.json` 的删除守卫会直接拦下项目内的 `rm`、`rmdir`、`unlink`、`find -delete`、`git clean` 等命令；删除 `_delete/` 里的东西会弹出确认，由用户批准。被拦下时不要换个写法绕过去，改为移进 `_delete/`。

## 各目录的约定

| 目录 | 约定 |
|---|---|
| `import/` | 收件箱。整理完应该是空的，只剩待确认的文件和 `README.md`。见 [import-routing](import-routing.md) |
| `research/` | `sources/` 放原始资料，**只读，永远不改**；`notes/` 放笔记和过程，可以迭代；`reports/` 放调研结论 |
| `docs/` | 文字为主的产出，包括排版过的 PDF。`brief/` 放需求和简报，其他按主题建子目录 |
| `design/` | 视觉为主的产出。`references/` 放参考（只读），`assets/` 放素材，其他按主题或页面建子目录 |
| 应用目录 | **不受**本项目命名标准约束，遵循所在技术生态的惯例；版本由 git 管理，不用 `_archive/`。多平台时按平台分子目录（`ios/`、`android/`、`web/`、`shared/`……）。README 写成开发文档 |
| `deliverables/` | 按交付批次建文件夹 `yymmdd-交付名/`。**批次交出后就冻结**，不再修改；要修正就出新批次。每个批次带一个 README 清单，写明包含什么、对应哪个源文件的哪个版本 |

## 结构

- 目录最多三层，人在 Finder 里点到第四层基本就迷路了。
- 子目录用到时再建；新建一个明确的子目录不用问。
- 某个目录平铺的文件**超过 12 个**，或者出现了明显的新类别时，提出分类方案，等用户确认后再迁移。
- 新建标准顶层目录用 `add_dir.py`，它会自动同步 `AGENTS.md` 的目录地图、`README.md` 的"去哪里找"和 `agent/trellis.json` 的 `dirs`。手动新建的目录，这三处要自己补。

## 人类可读

- 每个顶层产出目录都有一个用人话写的 `README.md`：这个目录放什么、怎么组织、最重要的几个文件是哪些。
- 优先使用人能直接打开的格式：md、pdf、png、csv。不要把给人看的结论放进 json 里。
- 移动或改名之后，用 grep 找出所有引用并修好链接。
